# USB 投屏 MVP

按照[构建与测试](build-and-test.zh_CN.md)构建并安装固件，然后打开
`PassportMirroring/PassportMirroring.xcodeproj`，运行 macOS App。
使用 USB 数据线连接一台 Passport，并在启动 App 前关闭串口监视器。
窗口会自动显示屏幕，拔插后会自动重连。烧录或打开串口监视器前，点击
**Release USB for Flashing**。接收端关闭串口描述符后画面暂停，此时可正常刷机；
完成后点击 **Resume Mirroring**，App 会重新连接。整个过程无需关闭 App。
同一个 USB Serial/JTAG 端口无法同时传输投屏和刷机数据。
本地开发 App 关闭了 App Sandbox，以便打开串口设备。

接收端匹配 Espressif USB Serial/JTAG VID `303a`、PID `1001`。
MVP 支持连接一台 Passport，仅提供实时显示。连接成功后连续七秒未收到有效镜像包时，
投屏暂停并提供手动重连入口，覆盖五秒的空闲关键帧周期，并预留两秒传输与调度余量。
每次打开串口后的首个有效镜像包等待仍为三秒；一幅完整关键帧可以分多块传输。
手动重连的总期限仍为五秒。串口读写错误仍会立即触发断开。

## 采集与传输

- LVGL `FLUSH_START` 在显示驱动交换字节前复制 RGB565 像素。固件把每个变化的
  240×320 像素直接放入容量固定为 24 项的行分段队列，
  不保留完整投屏帧缓冲。macOS 解码器把固定的 RGB565 数据直接转换为原生
  240×320 RGBA 帧，用于显示、截图和录制。
- 行队列占用约 12 KiB 内部 RAM。USB 任务另需 5,120 字节栈、1,024 字节发送缓冲、
  256 字节接收缓冲及驱动开销。分配失败时记录警告，本地显示继续运行。
- `sdkconfig.defaults` 将可选的 Wi-Fi 与 Wi-Fi RX 优化代码保留在 Flash。
  根据 Espressif 文档，两项配置合计释放超过 27 KB 内部 RAM。配合受限的 Station
  缓冲，投屏、TLS 与界面更新可以在无 PSRAM 的 ESP32-C3 上同时运行。
- 采集回调不会等待队列空间。增量采集会轮换选择变化区域，并在较高的窄区域内轮换
  选择分块。每次 LVGL 刷新最多发送一幅 20 行的独立增量帧，因此不会在
  `REFR_READY` 前占满队列。当完整行数据和帧结束包无法一起放入队列时，跳过该
  增量帧。压缩和阻塞式 USB 写入均在独立任务中执行。
- App 每 500 毫秒发送 ASCII `M`。固件在最近两秒收到过该请求时发送画面。
  LVGL 刷新的变化区域会立即进入传输。每五秒发送一幅完整关键帧，用于恢复丢包，
  并更新因增量帧过载而遗漏的像素。
- 关键帧按每块 20 行重新绘制和采集。上一块离开队列后才开始下一块，因此
  ESP32-C3 RAM 中无需保存 153,600 字节的完整图像。关键帧采集期间会忽略持续动画
  产生的无关刷新。所有分块使用同一个帧序号，最后只发送一个帧结束包。
- USB 任务与 LVGL 任务同为优先级 4，动画期间通过 FreeRTOS 时间片并行推进；
  阻塞式 USB 写入会主动让出 CPU。
- 控制台输出共用 USB 驱动队列。接收端跳过启动日志及其他字节，
  丢弃损坏或不完整的帧，并等待下一幅关键帧恢复。

## 第六版传输格式

每个行包包含一个水平分段。多字节整数使用小端序。协议只使用 240×320 RGB565
一种像素格式。每个包末尾附带对包头和载荷计算的 FNV-1a 校验值。

| 偏移 | 字节数 | 内容 |
| --- | --- | --- |
| 0 | 8 | ASCII `PMIRROW6` |
| 8 | 1 | 类型：`1` 为行分段，`2` 为帧结束 |
| 9 | 1 | 行包 bit 0 表示 PackBits；帧结束包 bit 0 表示关键帧；其余位必须为 0 |
| 10 | 2 | 帧序号，65535 后回到 0 |
| 12 | 2 | 行号，或帧结束包中的分段包数量 |
| 14 | 2 | 载荷字节数 |
| 16 | 可变 | 原始分段或按字节处理的 PackBits 数据；帧结束包为空 |
| 16 + 载荷长度 | 4 | FNV-1a：初值 2166136261，乘数 16777619 |

解码后的行载荷以 16 位小端起始列号开头，后面包含 1～240 个小端 RGB565 像素，
因此可以表示 LVGL 的部分宽度刷新区域，同一行也可以包含多个分段。
PackBits 控制字节最高位为 0 时，后续包含 `控制值 + 1` 个原始字节；最高位为 1
时，后续一个字节重复 `(控制值 & 0x7f) + 2` 次。压缩范围包含起始列字段和像素，
仅在结果更短时使用。

帧结束包中的数量表示该帧的行分段包数量。关键帧的有效分段必须覆盖全部
240×320 像素。接收端保留上一幅完整图像，应用有效的增量分段，并仅在帧边界通过
校验后显示。发送端与 macOS 接收端只实现固定的 `PMIRROW6` 格式。

240×320 RGB565 未压缩传输帧为 153,600 字节，30 fps 和 60 fps 的纯像素载荷分别约为
4.61 MB/s 和 9.22 MB/s。实际吞吐量取决于变化区域、PackBits 压缩率、USB 容量和
设备负载；连续的全屏高噪声内容无法维持这些速率。

协议测试已加入 `./tools/validate.sh --static`。在 macOS 上还会通过伪终端测试接收器，
覆盖五秒空闲关键帧、心跳发送、存在控制台流量时的停帧断开、断开后等待手动重连，
以及首帧超时。

## 设备验收

检查初始画面、页面切换、动画、RGB565 色块、方向、拔插重连、关闭并重新打开 App，
以及设备独立运行。测量静态 UI、局部动画和全屏动画的实际帧率，以及 UI 初始化后的
内部堆可用容量和最大连续块。构建与主机测试结果无法代替这些硬件检查结果。
